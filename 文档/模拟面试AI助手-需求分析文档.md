## 1. 项目概述

### 1.1 项目背景

校招求职竞争激烈，应届生普遍缺乏真实面试经验：不知道面试会问什么、回答缺少结构、临场容易紧张，且真人模拟面试（如就业指导老师、学长学姐）资源稀缺、成本高、不可反复练习。

大模型能力已能支撑高拟真度的模拟面试体验，本项目旨在通过 AI 面试官为校招应届生提供低成本、可反复、可量化反馈的模拟面试服务。

### 1.2 产品定位

面向**校招应届生**的 AI 模拟面试练习工具，以 **AI 实时生成题目 + 动态追问 + 多维度评估反馈**为核心能力，帮助用户在秋招/春招前高效备战。

### 1.3 产品形态

- **载体**：Web 网站（PC 端浏览器访问，便于演示与分享传播，后续可扩展移动端适配）
- **商业模式**：免费 + 会员制（基础面试次数免费，完整次数与不限次会员付费解锁）

## 2. 目标用户分析

### 2.1 用户画像

| 维度 | 描述 |
| ---- | ---- |
| 核心用户 | 求职季的应届毕业生（大三大四、研二研三） |
| 求职方向 | **不限技术岗**——覆盖 17 个方向，非技术岗占 9 个（产品、运营、行政、市场、人力、财务、客服、设计、教育） |
| 核心痛点 | 无面试经验、缺练习对象、回答无反馈、不知道薄弱点在哪 |
| 使用场景 | 宿舍/自习室利用碎片或整块时间练习，面试前一晚冲刺 |

### 2.2 用户核心诉求

1. 体验接近真实面试的问答过程（追问、压力感、真实面试官风格）
2. 面试后被明确告知"答得怎么样、差在哪、怎么改"
3. 看得见的进步（多次练习的能力成长曲线）

## 3. 核心业务流程

```
手机号验证码登录 → 完善求职档案（简历 / 目标岗位 / 考察方向）
        → 选择练习模式 + 面试官人设（+ 专项模式指定练哪一段）
        → 开始面试：AI 出题 ↔ 用户作答（语音或打字），AI 动态追问
        → 聊到建议时长 → 面试官自然收尾，问「还有没有想了解的」
              ├─ 回「没有了」→ 直接结束，出报告
              └─ 还有问题   → 面试官先回答，再接着聊
        → 查看五维评估报告 + 逐题复盘（亮点/不足/改进建议/参考答案）
        → 自动生成学习计划，历史数据沉淀，追踪成长
```

**初稿流程里被删掉的两个环节**：

- 「分享报告」—— 没有实现，相关字段已从数据库删除（见 §4.5）
- 「制定学习计划」保留，但**打卡功能已移除**（见 §4.7）

### 4.4 题目生成引擎

| 功能点 | 说明 | 优先级 | 状态 |
| ---- | ---- | ---- | ---- |
| AI 实时出题 | 大模型基于简历 + 目标岗位 + 考察方向生成面试题 | P0 | ✅ 已实现，带 10 轮对话记忆 |
| 题目质量控制 | 难度校准、去重、敏感内容过滤 | P0 | ⚠️ 做了**难度控制、去重、岗位主线约束**；**没有做敏感内容过滤** |
| 追问链生成 | 根据回答质量决定是否深挖、追问到什么深度 | P1 | ✅ 已实现（`parent_id` 自关联，多级追问） |
| 出题策略配置 | 题量、时长、难度梯度可配置 | P1 | ⚠️ **题量维度被推翻**：改成了"按建议时长 + 面试官自主收尾"，不再设题数上限。时长从字典表读，难度 1–5 可配 |
| 题库兜底 | — | — | ✅ **初稿说"不依赖预置题库"，实际做了反向决定**：加了 `question_bank` 表（88 道种子题），作为大模型不可用时的**第三级兜底**。原因见下 |

> **关于题库的决策反转**：初稿写的是"纯 AI 实时生成，不依赖预置题库"，并留了一句"建议评审时确认是否需要少量预置锚点题用于质量兜底"。
> 实际实现时确认了**需要**——因为大模型接口不稳定（网络抖动、限流、偶发非法输出），必须有兜底才能保证"用户永远能走完一场完整面试"。
> 最终优先级是四级：**大模型 → 规则追问 → 题库一选题 → 模板生成**。

### 4.5 评估反馈模块（面试后）

| 功能点 | 说明 | 优先级 | 状态 |
| ---- | ---- | ---- | ---- |
| 多维度评分报告 | 总分 + 分维度评分 | P0 | ✅ 已实现，**五个维度**：技术深度 0.30 / 表达逻辑 0.20 / 岗位匹配 0.20 / 临场表现 0.15 / 沟通表达 0.15。第一个维度按岗位自适应（技术岗=技术深度，非技术岗=专业能力） |
| 逐题点评复盘 | 每题展示问题、回答、参考答案、改进建议 | P0 | ✅ 已实现，含亮点/不足/改进建议/参考答案 |
| 报告导出/分享 | 支持保存/分享（网页链接、海报图） | P1 | ⛔ **已放弃**。数据库里原本有 `report_url`、`share_code` 两个字段，但从未实现分享链路，**这两列已删除** |
| 历史成长追踪 | 能力雷达图与趋势曲线 | P1 | ✅ 已实现，另有历史记录列表和学习计划 |

**评分机制的关键设计（初稿没写，后来补的）**：大模型只负责在六个预设档位里选一个分数并输出结构化 JSON，代码要做**类型 + 范围校验**（0–100 的数字），不合格整条作废、改用本地规则引擎；本地规则引擎**零随机数**，同一段回答算一百次都是同一个分数。报告生成失败时退回规则聚合，并标记 `generated_by=RULE`，前端显示提示条告知用户。

## 5. 非功能性需求

| 类别 | 要求 | 实际情况 |
| ---- | ---- | ---- |
| 性能 | 语音对话端到端延迟建议 < 2s；报告生成 < 1 分钟 | ✅ 语音不走后端（浏览器本地识别+合成），不存在端到端语音链路延迟；报告通常十几秒 |
| 出题体感 | — | ✅ **初稿没考虑，实际补的**：出题走 SSE 流式推送，题目文字逐块出现（打字机效果），首字延迟从几秒降到几百毫秒 |
| 可用性 | 面试中断（来电、切后台）后可恢复或明确提示重开 | ✅ 已实现：心跳 10 分钟自动结束 + 回来可续做 + 误点离开有确认框 |
| 内容安全 | 生成题目与点评需过滤敏感/歧视性内容；用户简历数据加密存储 | ⚠️ **没有做**：既没有敏感词过滤，简历也没有加密存储（只存服务器本地目录）。这是当前的缺口 |
| 合规 | 个人信息采集需明确授权；录音数据的留存策略需符合个保法 | ⚠️ **部分**：**本项目不存录音**（音频不出浏览器，只存转写文字），这一点天然合规；但简历数据没有字段级脱敏，也没有"导出我的数据/注销账号"入口 |
| 兼容 | 主流浏览器兼容，语音能力在不支持浏览器下要能降级 | ✅ 已实现降级：检测到不支持 Web Speech API 时提示换 Chrome/Edge，**始终保留纯文字输入**，功能不丢 |

## 6. 关键风险与结论

初稿列的 6 条风险，逐条给结论：

1. **语音延迟体验** —— ✅ **风险解除**。因为最终没用"云端 ASR → LLM → 云端 TTS"这条链路，而是用浏览器原生 API，语音根本不经过网络，不存在端到端延迟问题。
2. **浏览器语音能力兼容性** —— ⚠️ **存在**。目前 Chrome / Edge 支持好，Firefox / Safari 弱。缓解方式是检测能力并保留纯文字输入。
3. **支付合规** —— ⚠️ **存在且未解决**。当前是模拟支付；真接入需要营业执照（个人开发者拿不到微信/支付宝的网站支付资质）+ 域名 ICP 备案。这是上线的前置条件，不是技术问题。
4. **出题质量** —— ✅ **已缓解**。加了题库兜底（88 道种子题）+ 岗位主线约束 + 四级降级。
5. **评估一致性** —— ✅ **已缓解但未验证**。低温度（0.2）+ 六个固定档位 + 完全确定性的本地规则引擎；但**没有做过"模型打分 vs 专家打分"的一致性校验**，这是下一步最该补的。
6. **成本** —— ✅ **可控**。做了一处省钱设计：纯拒绝的回答（只说"不知道"且没补充）直接判 0 分，**不调用大模型**；另有四级降级减少无效调用。
